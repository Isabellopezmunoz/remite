Bloque 03

Estilos

Cómo se da estilo a un email: CSS inline en cada etiqueta, por qué no se usan clases, qué fuentes son seguras, cómo elegir colores y dónde poner el padding.

1. Todo el CSS va inline

Lo vimos de pasada en el Bloque 01: en un email el estilo va en el atributo style="" de cada etiqueta. Ahora el detalle de por qué, y de qué se pierde al hacerlo así.

Una web tiene tres formas de aplicar CSS: hoja externa, bloque <style> e inline. En email solo la última es de fiar:

Forma de poner CSS ¿Funciona en email?
Hoja externa <link rel="stylesheet"> ❌ No. Los clientes no descargan CSS externo.
Bloque <style> en el <head> ⚠️ A veces. Muchos lo eliminan o lo ignoran (Gmail histórico, apps).
Inline, style="" en la etiqueta ✅ Sí. Es lo único que funciona en todos lados.
El <style> no es inútil del todo. Se usa para lo que no se puede hacer inline: media queries (responsive), :hover, o estilos de dark mode. Pero como cualquier cliente puede ignorarlo, el email tiene que verse bien sin él. El <style> es una mejora, nunca la base.

2. Por qué no se usan clases

Si los clientes eliminan el <style>, una clase como class="destacado" se queda sin definición: apunta a reglas que ya no existen. La etiqueta pierde su estilo entero.

Clase vs. inline cuando el cliente borra el <style>

Con clase — el cliente borró el <style>:

Texto sin estilo (la clase no apunta a nada)

Con inline — el estilo viaja pegado:

Texto con su color y peso intactos

<!-- ❌ Si se borra el <style>, esto queda sin estilo -->
<p class="destacado">Texto</p>

<!-- ✅ El estilo está en la etiqueta: no depende de nada -->
<p style="color:#8b76c4; font-weight:700; margin:0;">
  Texto
</p>

El precio es repetir estilos: si quince celdas llevan el mismo color de texto, escribes ese color quince veces. Es tedioso — por eso existen los inliners — pero es el motivo de que en este proyecto se haga a mano primero: para entender qué problema resuelven esas herramientas.

3. Fuentes: solo las web-safe

Las fuentes personalizadas (Google Fonts, @font-face) no cargan de forma fiable en email — Outlook directamente las ignora. Se usan fuentes web-safe: las que ya vienen instaladas en casi cualquier ordenador y móvil.

Arial / Helvetica
Hola, este es el texto
Georgia (con serifa)
Hola, este es el texto
Verdana
Hola, este es el texto
Tahoma / Trebuchet
Hola, este es el texto

Siempre con "fallback"

La font-family se escribe como una lista: la fuente que quieres primero y, detrás, alternativas cada vez más genéricas. Si el cliente no tiene la primera, baja a la siguiente. La última siempre es una familia genérica (sans-serif o serif).

font-family con fallback

Este párrafo intenta Arial → Helvetica → cualquier sans-serif. 

<td style="font-family:Arial, Helvetica, sans-serif;
            font-size:16px; color:#3a3550;">
  Texto del email
</td>
La fuente se repite en cada celda de texto. No se hereda de forma fiable de una tabla a otra en email, así que la font-family y el font-size se ponen en cada <td> que tenga texto. Otra vez: repetición a propósito.

4. Colores

Los colores se escriben en hexadecimal de 6 dígitos — #8b76c4, no #87c abreviado — porque algunos clientes no entienden la versión corta. Nada de rgba() ni colores con nombre para cosas importantes: hex de 6 dígitos y a lo seguro.

Esta es la paleta pastel que usa este proyecto, como referencia:

Lavanda fuerte#8b76c4
Lavanda#d8cef0
Lavanda claro#f3f0fb
Melocotón fuerte#e0916a
Melocotón#f5cbb0
Tinta#3a3550
Pon siempre el color de fondo, aunque sea blanco. Con el dark mode, algunos clientes invierten los colores: si una celda no declara background-color, puede acabar con un fondo oscuro y el texto ilegible. Declarar #ffffff de forma explícita lo evita en parte.

5. Espaciado: padding en las celdas

Esta es la regla de oro del espaciado en email: el espacio se crea con padding dentro de los <td>, no con margin. El margin es poco fiable — Outlook lo ignora en muchos casos — mientras que el padding de una celda se respeta en todas partes.

El aire alrededor del texto = padding del td
El padding de 28px es este aire de alrededor 
<!-- El padding va en el td, no margin en lo de dentro -->
<td style="padding:28px; background-color:#fdf0e7;">
  El contenido respira gracias al padding de la celda
</td>

<!-- padding también admite la forma de 4 valores: -->
<!-- arriba  derecha  abajo  izquierda -->
<td style="padding:20px 24px 32px 24px;"> ... </td>

¿Y el espacio entre dos bloques?

Para separar dos secciones (p. ej. el cuerpo del pie) hay dos vías fiables: dar padding generoso a las celdas que se tocan, o meter una fila espaciadora — un <tr> vacío con una altura fija. La fila espaciadora es muy de email:

Fila espaciadora entre bloques
Bloque de arriba
Bloque de abajo
<tr>
  <td style="background-color:#f3f0fb; padding:14px;">
    Bloque de arriba
  </td>
</tr>

<!-- Fila espaciadora: una celda vacía con altura fija -->
<tr>
  <td height="24" style="height:24px; line-height:24px;
            font-size:0;">&nbsp;</td>
</tr>

<tr>
  <td style="background-color:#fdf0e7; padding:14px;">
    Bloque de abajo
  </td>
</tr>
Por qué font-size:0 y el &nbsp;: la celda vacía lleva un espacio (&nbsp;) para que Outlook no la colapse, y font-size:0 + line-height igual a la altura para que ese espacio no añada altura de más. Trucos pequeños, pero hacen que la separación sea exacta en todos los clientes.

6. Texto legible

Para que el texto del email se lea bien y de forma consistente, cada <td> con texto suele declarar estas cuatro cosas:

  • font-family — la lista web-safe con fallback.
  • font-size — 14–16px para cuerpo; menos de 14 se lee mal en móvil.
  • line-height — alto de línea, ~1.5 del tamaño de fuente, para que respire.
  • color — hex de 6 dígitos.
Una celda de texto bien estilada
Un párrafo con su fuente, su tamaño, su alto de línea y su color. Así se lee cómodo en cualquier cliente de correo. 
<td style="font-family:Arial, Helvetica, sans-serif;
            font-size:16px;
            line-height:24px;
            color:#3a3550;
            padding:20px;">
  Un párrafo con su fuente, tamaño, alto de línea y color.
</td>
El line-height, mejor en píxeles. Outlook se comporta de forma rara con line-height sin unidad o en porcentaje. Ponerlo en píxeles (line-height:24px) es lo más predecible.

7. La media query: la excepción del <style>

Quedó pendiente del Bloque 02: para que dos columnas se apilen en el móvil hace falta una media query, y eso solo se puede escribir en un <style> de la cabecera — inline no admite media queries.

La clave es que sea una mejora opcional: el email se ve correcto sin la media query (las columnas quedan estrechas pero funcionan); con ella, además, se ven mejor en móvil. Si un cliente ignora el <style>, no se rompe nada.

<style> con media query para apilar columnas

En escritorio: columnas lado a lado.
En móvil (< 600px): cada columna al 100%, apiladas. 

<!-- En el <head> del email -->
<style>
  @media screen and (max-width: 600px) {
    /* la clase solo se usa aquí, como gancho */
    .columna-movil {
      width: 100% !important;
      display: block !important;
    }
  }
</style>

<!-- En el cuerpo: la celda lleva clase Y estilo inline -->
<td class="columna-movil" width="300"
    style="width:300px; padding:20px;">
  Columna
</td>
Aquí sí se usa una clase — pero solo como "gancho" para la media query, nunca para el estilo base. El estilo base sigue inline (width:300px); la clase solo lo sobrescribe en móvil. Por eso lleva !important: tiene que ganarle al inline.
Recapitulando: CSS inline siempre, clases solo como gancho de media queries, fuentes web-safe con fallback, hex de 6 dígitos, fondos siempre declarados y espaciado con padding en celdas o filas espaciadoras. Con los tres bloques hechos, ya tienes la base — lo siguiente son las plantillas reales.
